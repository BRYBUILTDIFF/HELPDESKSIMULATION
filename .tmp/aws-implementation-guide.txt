Purpose
This document consolidates the complete working implementation of the browser-based Windows simulation environment used by the Help Desk system. It covers the AWS network, Windows Server 2025 image, isolated per-session EC2 provisioning, Apache Guacamole, security groups, backend integration, environment variables, troubleshooting decisions, and cost-control procedures.

Security Notice
Credentials previously exposed during setup must not be reused.
AWS access keys, the Guacamole JSON secret, and the Windows lab password were displayed during troubleshooting. The final setup should use newly generated values. This guide intentionally uses placeholders instead of reproducing any exposed secret.
Rotate the IAM access key before using the environment again.
Generate a new 32-hex-character GUAC_JSON_SECRET and use the same value in Ubuntu and Express.
Use a new hidden password for the Windows lab account before creating the final reusable AMI.
Never commit server/.env, PEM private keys, or credentials to Git.
Never expose AWS access keys, Windows passwords, Guacamole secrets, AMI controls, or private EC2 addresses to the React client.

1. Final System Overview
The Help Desk system provides a real Windows desktop inside the browser. A learner starts a simulation from the React application. The Express backend creates one temporary Windows Server 2025 EC2 instance for that simulation session. Apache Guacamole then connects to the Windows VM over private RDP and streams the desktop to the browser using HTML5.
Key architectural rule
Users never receive direct RDP access. The Windows VM has no public IP and accepts TCP 3389 only from the Guacamole security group. Every simulation receives a fresh Windows VM and the VM is terminated when the session ends or expires.
User Browser   |   | HTTP/HTTPS   vReact Help Desk Application   |   | authenticated API   vExpress Backend   |   | AWS SDK   vAWS EC2   |   +--> Temporary Windows Server 2025 VM (private subnet, no public IP)   |   +--> Guacamole Gateway (Ubuntu, public subnet)              |              | private RDP TCP 3389              v        Windows Server 2025
Application control: React and Express decide when a user may create, connect to, and terminate a simulation.
Infrastructure control: the AWS Launch Template decides the AMI, instance type, subnet, storage, metadata policy, and security group used by Windows.
Remote desktop delivery: Guacamole/guacd performs RDP and exposes an HTML5 desktop to the browser.

3.1 Public subnet
The public subnet is used for the Guacamole gateway and temporary master/diagnostic hosts when direct administration is required.
Public route tableDestination      Target10.0.0.0/16     local0.0.0.0/0       Internet Gateway
The Guacamole EC2 instance must have Auto-assign public IPv4 enabled when no stable public address/domain is used.
3.2 Private subnet
All student Windows simulation VMs launch into the private subnet. They do not need a public IPv4 address because Guacamole reaches them through their private 10.0.x.x address.
Private subnet  |  +-- Windows Server 2025 VM      Private IPv4: 10.0.x.x      Public IPv4: none
Important lesson from troubleshooting
The original Windows master was created in the AWS default VPC (172.31.0.0/16) while the rebuilt Guacamole server was in helpdesk-simulation-vpc (10.0.0.0/16). That mismatch caused Guacamole to report that the remote desktop server was unreachable. The Launch Template was corrected so all new Windows simulations use the Help Desk private subnet.

5. Windows Server 2025 Master and Custom AMI
The final OS is Microsoft Windows Server 2025 Base (Desktop Experience), not Windows Server 2022 and not Server Core.
Step 1 - Launch the temporary master
Name: helpdesk-windows-2025-masterAMI: Microsoft Windows Server 2025 BaseInstance type: t3.smallVPC: helpdesk-simulation-vpcSubnet: public subnet (temporary master only)Public IPv4: enabled (temporary)Security group: helpdesk-windows-sgStorage: 30 GiB gp3, encryptedMetadata: IMDSv2 required
For the temporary master, add a temporary RDP 3389 rule from My IP so the administrator can configure the desktop.
Step 2 - Retrieve the Administrator password and connect by RDP
Wait for the EC2 instance to be Running and pass status checks.
Use EC2 > Connect > RDP client > Get password.
Decrypt the password with the matching PEM key.
Connect to the instance public IPv4 using mstsc.
Run winver and confirm Windows Server 2025.
Step 3 - Configure the Windows image
Enable Remote Desktop and Windows Firewall Remote Desktop rules.
Set TermService startup type to Automatic and verify it is Running.
Verify TCP 3389 is listening.
Create the local labuser account.
Add labuser to Remote Desktop Users.
Prepare Help Desk tools, shortcuts, sample files, and simulation scenarios.
Remove unnecessary EC2 Feedback / EC2 Microsoft Windows Guide shortcuts from the user/default/public desktops.
Install Windows updates and reboot.
Remove browser history, credentials, personal files, and temporary installers.
Step 4 - Prepare a reusable image
Use EC2Launch/Sysprep preparation, then create a custom AMI after Windows is clean and RDP/labuser have been tested. The resulting image becomes the template for every learner session.
Example AMI name:helpdesk-windows-server-2025-v1
Sysprep system-log behavior observed
New instances initially showed SysprepState=IMAGE_STATE_UNDEPLOYABLE during early boot, then completed Sysprep configuration, created the RDP certificate, and eventually logged 'Message: Windows is Ready to use'. The early UNDEPLOYABLE line was not the final state.

9. Nginx and Direct Launch Page
Nginx exposes Guacamole on port 80 during local development while Guacamole itself remains bound to 127.0.0.1:8080.
server {    listen 80;    server_name _;    location = /guac-launch.html {        root /var/www/html;        add_header Cache-Control "no-store, no-cache, must-revalidate";        add_header Pragma "no-cache";        expires -1;    }    location /guacamole/ {        proxy_pass http://127.0.0.1:8080;        proxy_buffering off;        proxy_http_version 1.1;        proxy_set_header Host $host;        proxy_set_header X-Real-IP $remote_addr;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $scheme;        proxy_set_header Upgrade $http_upgrade;        proxy_set_header Connection "upgrade";    }}
9.1 Direct-launch page
The launcher prevents users from seeing the Guacamole home screen or having to manually logout/re-login when stale Guacamole browser authentication exists.
iframe  -> /guac-launch.html?data=<encrypted-token>  -> clear stale Guacamole browser auth state  -> /guacamole/?data=<encrypted-token>  -> open Windows connection
10. Guacamole JSON Authentication
The system uses Guacamole JSON authentication so Express can provide a short-lived signed/encrypted connection definition without exposing the Windows password to React.
Step 1 - Generate the shared secret
openssl rand -hex 16
This produces 32 hexadecimal characters. The same value must be present in both Ubuntu and Express.
Ubuntu ~/guacamole/.envGUAC_JSON_SECRET=<NEW_32_HEX_SECRET>Express server/.envGUAC_JSON_SECRET=<THE_EXACT_SAME_SECRET>
Important troubleshooting result
An early Invalid Login problem was caused because the running Guacamole container had JSON_ENABLED=true but JSON_SECRET_KEY length 0. Editing .env alone did not update the existing container. The container had to be recreated after the secret was set.
Step 2 - Docker Compose environment
JSON_ENABLED: "true"JSON_SECRET_KEY: "${GUAC_JSON_SECRET:?GUAC_JSON_SECRET is required}"
Step 3 - Recreate containers after secret/config changes
cd ~/guacamolesudo docker compose downsudo docker compose up -d --force-recreatesudo docker compose ps
Step 4 - Verify the key is inside the running container
sudo docker inspect helpdesk-guacamole \  --format '{{range .Config.Env}}{{println .}}{{end}}' |  awk -F= '/^JSON_SECRET_KEY=/{print "JSON_SECRET_KEY length:", length($2)}'
Expected: JSON_SECRET_KEY length: 32.
10.1 RDP connection payload
{  "username": "helpdesk-<userId>-<sessionId>",  "expires": <short-lived epoch milliseconds>,  "connections": {    "Windows Help Desk Lab": {      "protocol": "rdp",      "parameters": {        "hostname": "<session.privateIp>",        "port": "3389",        "username": "labuser",        "password": "<backend-only password>",        "security": "any",        "ignore-cert": "true"      }    }  }}
The working configuration ultimately used automatic RDP security negotiation (security: "any") instead of forcing NLA. During troubleshooting, guacd logs showed Security mode: NLA followed by Server refused connection (wrong security type?), which isolated the issue to RDP security negotiation.

14. API and Frontend Lifecycle
Endpoint
Responsibility
POST /api/simulation-sessions
Validate user/module/limits; create session; launch EC2; return PROVISIONING.
GET /api/simulation-sessions/:id
Return status only; refresh EC2 state; do not regenerate Guacamole URLs repeatedly.
POST /api/simulation-sessions/:id/connect
Verify ownership + READY/ACTIVE; generate one fresh Guacamole URL.
POST /api/simulation-sessions/:id/end
Terminate the exact session EC2 instance; mark ENDED.
14.1 Frontend state machine
IDLE  -> PROVISIONING  -> READY  -> CONNECTING  -> ACTIVE  -> TERMINATING  -> ENDED / FAILED
Do not render the Guacamole iframe during PROVISIONING.
Stop status polling when the backend reaches READY.
Call the connect endpoint exactly once per connection attempt.
Mount one iframe only after a valid Guacamole URL is returned.
Clear the iframe immediately when ending the simulation.
A reconnect should request a fresh Guacamole token; it should not create another EC2 instance unless the current VM is no longer usable.
15. End-to-End Execution Flow
1. User opens a module where simulation.surface = "windows-os".2. User clicks Start Simulation.3. React POSTs /api/simulation-sessions.4. Express validates authentication, module surface, per-user limit, global limit, and config.5. Express creates SimulationSession(status=PROVISIONING).6. Express calls RunInstances with the Launch Template default version.7. AWS launches Windows Server 2025 in the private subnet.8. Backend describes the instance until it is running and has a private IPv4.9. Windows completes EC2Launch/Sysprep and becomes RDP-ready.10. Session becomes READY.11. React stops polling and POSTs /connect once.12. Express creates a short-lived encrypted Guacamole JSON token.13. React mounts the iframe with GUACAMOLE_LAUNCH_URL?data=<token>.14. guac-launch.html clears stale Guacamole browser authentication and redirects.15. Guacamole authenticates the JSON payload.16. guacd connects to Windows private-ip:3389 using labuser.17. User sees the Windows Server 2025 desktop.18. User completes or ends the simulation.19. React clears the iframe and POSTs /end.20. Express calls TerminateInstances.21. SimulationSession becomes ENDED.

Resolution

19. Final Production Recommendations
Move Guacamole from plain HTTP to HTTPS before real learners use the environment.
Use a stable hostname instead of embedding a changeable EC2 public IP in application configuration.
Use IAM roles/temporary credentials when the backend is deployed on AWS instead of long-lived IAM user keys.
Tighten IAM permissions around the specific Launch Template, tags, and instance profile.
Keep Windows RDP private and never expose 3389 to 0.0.0.0/0.
Retain the same internal module surface value: windows-os.
Use visible UI wording that matches the actual OS: Windows Server 2025, not Windows 11, unless true Windows 11 is later implemented.
Make READY represent RDP usability, not only EC2 running state.
Add budgets/alarms for EC2, EBS snapshots, public IPv4 usage, and unexpected instance counts.
Store production secrets in a dedicated secrets service or protected deployment environment.

Appendix A - Daily Operations Runbook
A.1 Start of development/test session
1. Confirm helpdesk-guacamole is Running.
2. Confirm its current public IPv4 matches GUACAMOLE_BASE_URL and GUACAMOLE_LAUNCH_URL.
3. SSH to Guacamole and run sudo docker compose ps.
4. Confirm helpdesk-guacamole and helpdesk-guacd are Up.
5. Start the Express backend and React frontend.
6. Start one Windows simulation and confirm the new instance is created in the Help Desk private subnet.
7. Verify the simulation opens Windows directly in the iframe.
A.2 End of development/test session
1. End any active simulation from the application.
2. Verify the Windows simulation EC2 instance terminates.
3. Terminate any manual diagnostic Windows VM that is no longer required.
4. Optionally stop Guacamole to save compute when the simulator will not be used.
5. If Guacamole is stopped/started later and receives a new public IP, update both Guacamole URLs in server/.env and restart Express.
